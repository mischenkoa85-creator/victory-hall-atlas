API action: return_for_rework (той самий POST tasks/{task}/transitions).
Поля: idempotency_key, expected_version, action, reason.
Actor/role/reviewer/version звіту із HTTP не приймаються.

SQL006 змінює лише існуючі board_transition, board_task_get, board_task_list та
додає приватний readonly helper _board_rework_view. Таблиці й GRANT реальним
користувачам не змінюються. Frozen SQL001–005 не редагуються.

Повернення: лише записаний reviewer із board.review, лише reported_done із
review_required=true, без самоприймання. Пояснення обов'язкове.
Результат: status=assigned, display_state=returned_for_rework,
last_action=return_for_rework, ETA=NULL, старий assignee лишається.
Reviewer може перепризначити, worker повинен знову натиснути accept.
Після accept status/display_state=in_progress; reason повернення доступний
у rework_reason/rework_requested_at/rework_request_version та в історії.

Результат читається за тією самою scope/privacy перевіркою. Helper не має PUBLIC
або reader EXECUTE. Він читає події лише до task.version; новіші concurrent events
не домішуються до старішого snapshot рядка. VOLATILE потрібен для видимості
щойно вставленої події у відповіді write-функції.

Report version не зменшується. Report/photo записи лишаються immutable.
Наступний report_done після повернення потребує completion attachment цього
worker/task, завантаженого ПІСЛЯ останнього rework event. Old reference не приймається.
Це доводить час нового завантаження, а не час знімання або фізичне виконання роботи.
Повтор уже COMMITTED старого report_done із тим самим ключем повертає стару
квитанцію до freshness guard, тому idempotency не ламається.

Один event/command/audit; три окремі outbox audience: assignee, creator, administrator.
Жодних email/Telegram/push відправлень. SQL transaction, optimistic version,
durable cancellation та ідемпотентність використані без зміни протоколу.
